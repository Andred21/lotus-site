## 3. Decisões

### D0 — Sem Context Packet · Claude

As duas EAP foram lidas direto do data source do Notion. O resto é repositório e medição local
feita nesta sessão (REST pública do WordPress, `curl`, `unzip -l` do backup existente, `gh run
list` do corporativo). Mesmo tratamento de `B2` e `B3`.

### D1 — O rollback do corte tem duas camadas · Claude + Medido

1. **Rápida — DNS.** O WordPress continua servindo em `185.146.167.195` / `2a07:7800::195` até
   `B7`. Voltar é pôr apex e `www` de novo nesses endereços no Route 53. O tempo de volta é o TTL
   do que os resolvedores guardaram: o alias do CloudFront, não o registro do WordPress (D12).
2. **Desastre — backup.** Se o host perder o WordPress, a volta é restaurar o backup.

A camada 1 é a que o corte usa. A camada 2 é o seguro dela e é também a matéria-prima do "backup
final" que `B7` exige.

### D2 — Backup novo pelo StackCP; o WPvivid de 2025 é segunda cópia · `S-JOAO` + Medido

Medido em 2026-09-28:

- existe um backup WPvivid completo de **2025-07-25** (`backup_all.zip`, 199557444 B:
  banco, temas, plugins, uploads, `wp-content`, core), feito com WP 6.8.2 e PHP 7.4.33;
- o conteúdo não mudou desde então: a REST pública lista duas páginas modificadas por último em
  2025-07-24, zero posts e mídia de 2022;
- o código mudou: o WordPress no ar é **7.1.2** (`<generator>` do feed), por atualização
  automática. PHP continua 7.4.33. O WPvivid 0.9.117 continua instalado;
- **João não tem login no `wp-admin`.**

Sem login, o backup novo sai do StackCP — arquivos do site e dump do banco —, não do WPvivid. É
esse backup que a restauração exercita, porque é o que bate com o que está no ar. O de 2025 fica
como segunda cópia, sem ensaio.

### D3 — Guarda: Windows + uma cópia do João fora dele; o repo só guarda hash · `S-JOAO`

As cópias ficam no Windows do João e numa segunda mídia escolhida por ele. O repositório registra,
por arquivo: SHA-256, tamanho, data de geração, versão do WordPress e onde a cópia está — descrição,
não caminho com segredo.

O bucket `lotus-site-prod` está **vetado** para isso, por medição: a distribuição serve qualquer
chave dele — `releases/<sha>/index.html` responde 200 pelo domínio do CloudFront —, então um dump
ali seria público. O dump carrega hash de senha de usuário; o `wp-config.php`, a senha do banco e
os salts.

### D4 — A restauração é exercitada sob o próprio hostname, sem reescrever o banco · Claude

O Elementor guarda URL absoluta dentro de metadado serializado, e search-replace que muda o
tamanho da string corrompe o serializado. Em vez de reescrever o banco, o ensaio serve a cópia
restaurada **como `https://lotusotec.cl`**: Apache com TLS autoassinado num container, e o Chromium
com `lotusotec.cl` e `www.lotusotec.cl` resolvidos à força para `127.0.0.1`. O banco restaurado é
byte a byte o do dump; só as constantes de conexão de uma **cópia** do `wp-config.php` mudam.

A resolução forçada também é a garantia de que nada da página veio do site vivo.

Restaurar no próprio StackCP não é exercitado — tocaria produção. O procedimento fica escrito,
junto da recuperação de senha do administrador pelo phpMyAdmin, que é a saída para a falta de login
de D2.

### D5 — O domínio próprio entra na distribuição neste bloco · `S-JOAO`

Aliases `lotusotec.cl` e `www.lotusotec.cl`, certificado do ACM e redirect `www` → apex saem de `B5`
e entram aqui. Com isso o smoke roda contra o domínio real — certificado real, `Host` real, CSP sob
a origem real — antes de o DNS virar, e `B5` fica reduzido a DNS, `X-Robots-Tag` e `D-39`.

Anexar aliases a uma distribuição não muda nada para o visitante enquanto o DNS aponta para o
WordPress.

### D6 — Redirect `www` → apex por CloudFront Function · Claude + Medido

Medido: o WordPress responde `https://www.lotusotec.cl/` com **301** para `https://lotusotec.cl/`, e
`http://lotusotec.cl/` com **301** para `https://lotusotec.cl/`. O clone precisa do mesmo.

`http` → `https` já é do `ViewerProtocolPolicy: redirect-to-https`. `www` → apex é uma CloudFront
Function (`cloudfront-js-2.0`, `viewer-request`) só no behavior padrão: host `www.lotusotec.cl`
devolve 301 para `https://lotusotec.cl` + caminho + query; qualquer outro host segue. O domínio do
CloudFront continua servindo o site, o que o smoke e a depuração usam.

`/api/*` fica sem a função: o formulário é same-origin no apex, e um `POST` redirecionado perde o
corpo.

Descartados: segunda distribuição ou bucket de redirect (infra demais para uma regra); servir `www`
com 200 e confiar no canonical (quebra paridade com o WordPress).

`http://www.lotusotec.cl/` faz dois saltos (`https://www…`, depois o apex): o redirect de protocolo
acontece antes da função. Aceito; o smoke registra a cadeia.

### D7 — O rollback DNS é ensaiado num nome descartável · `S-JOAO`

`ensaio-corte.lotusotec.cl` percorre, no stack `lotus-dns`, o mesmo caminho que `B5` vai usar, e
também o caminho de emergência. Os estágios estão em §4.4. O ensaio mede **DNS**, não HTTP: a
distribuição responde 403 para um host fora dos `Aliases`, e isso é esperado.

**Condição de parada:** se o Route 53 recusar alias para a distribuição num nome que não está nos
`Aliases`, o ensaio para e o desenho volta à spec. Nada é contornado na hora.

### D8 — Janela do rollback: `B5` corta até 2026-10-27 · `S-JOAO` + Medido

O WordPress serve um certificado Let's Encrypt válido até **2026-11-10T20:37:55Z** e sem caminho de
renovação desde a delegação (`D-51`). Depois do corte, o HSTS do clone (`max-age=31536000`, D1 de
`B3`) fixa HTTPS em `lotusotec.cl` por um ano no navegador de quem visitou: voltar para o WordPress
com o certificado vencido é erro de TLS sem opção de prosseguir.

Regra: `B5` só corta até **2026-10-27** — catorze dias de estabilização com rollback possível —, a
menos que `D-51` esteja resolvido antes. O procedimento de rollback abre com a verificação da
validade do certificado do WordPress.

### D9 — Smoke: Playwright com config própria e nove itens · `S-JOAO`

`pnpm smoke`, fora de `pnpm check` e de `pnpm e2e`, porque depende de rede e de produção. O mesmo
comando serve `B5` antes de virar o DNS (domínio forçado) e depois (resolução normal). Itens em
§4.5.

Descartados: script só em Node (não prova JS rodando, console nem Turnstile no host real); reusar
as specs de `e2e/` (simulam o Turnstile e `/api/contacto` com `page.route`, o que esconde
exatamente o que o smoke precisa ver).

### D10 — O artefato é identificado pela própria distribuição · Medido

Medido em 2026-09-28: o último `CI` verde de `Gatika-CL/lotus-site` em `main` é `ca8f49b`
(2026-09-28T01:05Z), e `index.html` da raiz é idêntico, em SHA-256, a
`/releases/ca8f49bcd3ae1e94b7769de741b26b9daef8cdeb/index.html`, ambos servidos pela distribuição.
O item 1 do smoke não precisa de credencial AWS.

O relatório do smoke nomeia esse SHA. `B5` só vira o DNS se o SHA no ar for o mesmo que passou; se
qualquer deploy acontecer entre os dois, o smoke roda de novo.

### D11 — O envio real do formulário é humano · Claude

O Turnstile real tende a recusar navegador automatizado. O smoke automatizado prova que o widget
carrega no host real e que `/api/contacto` recusa o que deve recusar. O envio de uma mensagem real
é de João, num navegador com `lotusotec.cl` forçado para a distribuição, e a prova é a mensagem
recebida em `contacto@lotusotec.cl`.

A spec de `B2` mandou o widget aceitar `lotusotec.cl` e `www.lotusotec.cl`, e a função não confere
hostname. O envio real é o que prova que a configuração do widget segue a spec.

### D12 — O TTL que governa o rollback é o do alias · Claude, a medir

Apex e `www` têm TTL 3600 hoje (`TtlPadrao` de `infra/lotus-dns.yaml`). Isso governa quanto demora o
**corte** para propagar — problema de `B5`. O rollback substitui o alias do CloudFront, cujo TTL a
AWS fixa em 60 s. O ensaio de D7 mede os dois números; o procedimento usa os medidos, não estes.

### 4.2 Forma do template

Em `Distribuicao.DistributionConfig`:

```yaml
Aliases:
  - lotusotec.cl
  - www.lotusotec.cl
ViewerCertificate:
  AcmCertificateArn: !Ref ArnDoCertificadoDoDominio
  SslSupportMethod: sni-only
  MinimumProtocolVersion: TLSv1.2_2021
DefaultCacheBehavior:
  # ...o que já existe...
  FunctionAssociations:
    - EventType: viewer-request
      FunctionARN: !GetAtt RedirecionarWww.FunctionMetadata.FunctionARN
```

`ArnDoCertificadoDoDominio` é parâmetro com `AllowedPattern` preso a `arn:aws:acm:us-east-1:` — o
CloudFront só aceita certificado dessa região. O valor é a saída `ArnDoCertificado` do stack
`lotus-dns` (`us-east-1`), passado no change set como `ArnDaFuncaoDeContato` é hoje.

`RedirecionarWww` é `AWS::CloudFront::Function` com `AutoPublish: true`, código inline. O código
monta a query de volta a partir de `event.request.querystring`, inclusive chave com vários valores.

A catraca (`pnpm check`, sem rede) reprova quando:

- os `Aliases` diferem dos nomes do `Certificado` de `infra/lotus-dns.yaml` (`DomainName` +
  `SubjectAlternativeNames`);
- a função aparece em qualquer behavior além do padrão, ou falta nele;
- o código da função, extraído do YAML e rodado em `node:vm`, não devolve 301 com `location`
  exato para `www` com caminho, sem caminho e com query de chave repetida, ou mexe em pedido de
  outro host.

### 4.3 Ensaio de restauração

1. João baixa do StackCP os arquivos do site e o dump do banco e diz onde estão. Claude registra
   SHA-256 e tamanho das duas cópias e do WPvivid de 2025.
2. `ensaio-restauracao.sh <arquivos> <dump>` recusa qualquer caminho dentro da árvore do repo,
   descompacta num diretório temporário, troca `DB_NAME`, `DB_USER`, `DB_PASSWORD` e `DB_HOST` na
   cópia do `wp-config.php`, importa o dump no MariaDB e sobe o Apache em `127.0.0.1:443`.
3. `verificar-restauracao.mjs` abre `https://lotusotec.cl/` duas vezes: uma com resolução normal (o
   WordPress vivo), outra forçada para `127.0.0.1` e aceitando o certificado autoassinado (a cópia).
4. Passa quando: home restaurada 200; `<title>`, H1 e texto visível iguais aos do vivo; toda resposta
   de `lotusotec.cl` na cópia com status < 400; `wp-login.php` 200; log do container sem `PHP Fatal
error`.
5. O script derruba containers e volumes e apaga o diretório temporário, inclusive quando falha.

### 4.4 Ensaio DNS

Cada estágio é um commit no `infra/lotus-dns.yaml` (com a catraca de `zona.mjs` acompanhando) e um
change set executado por João, salvo o 4b, que é chamada direta. `medir-propagacao.mjs` roda em
cada um contra os NS do Route 53 e contra `8.8.8.8`, `1.1.1.1` e `9.9.9.9`, e os resolvedores são
consultados antes de cada troca, para que o cache exista como existiria no corte.

| Estágio | O que muda em `ensaio-corte`                                    | O que mede                                 |
| ------- | --------------------------------------------------------------- | ------------------------------------------ |
| 1       | nasce `A` + `AAAA` → WordPress, TTL `TtlPadrao`                 | linha de base                              |
| 2       | vira alias → distribuição                                       | propagação do **corte**                    |
| 3       | `git revert` do estágio 2, change set                           | volta pelo **caminho principal**           |
| 4a      | alias de novo, change set                                       | —                                          |
| 4b      | `UPSERT` direto com o batch no formato de `rollback-corte.json` | volta pelo **caminho de emergência**       |
| 4c      | template volta ao WordPress, change set                         | se a reconciliação passa, falha ou é no-op |
| 5       | registro removido                                               | nome não resolve mais                      |

São seis change sets e uma chamada direta. O estágio 4c é o que responde se o `UPSERT` fora do
CloudFormation deixa o stack num estado de onde ele sai sozinho; se não sair, o ensaio registra a
saída que funcionou e ela entra no procedimento.

O procedimento de `docs/infra/rollback-corte.md` escolhe o caminho principal pelo resultado, e
traz: pré-checagens (WordPress respondendo por `curl --resolve lotusotec.cl:443:185.146.167.195`;
validade do certificado dele contra D8), gatilho (itens 2 a 6 do smoke falhando depois do corte),
os dois caminhos com comandos exatos, a reconciliação, e o que conferir depois de voltar.

### 4.5 Smoke

Variáveis: `SMOKE_URL` (ex. `https://lotusotec.cl`), `SMOKE_VIA` opcional (o domínio da
distribuição; resolvido para um IPv4 no início, e esse IP vira `--host-resolver-rules` do Chromium
e `lookup` das requisições em `node:https`), `SMOKE_SHA` opcional (sem ele, o SHA vem do último
`CI` verde do corporativo, por `gh run list --repo Gatika-CL/lotus-site`).

| #   | Item        | Passa quando                                                                                                         |
| --- | ----------- | -------------------------------------------------------------------------------------------------------------------- |
| 1   | Artefato    | `index.html` servido ≡ `/releases/<SHA>/index.html` em SHA-256; o relatório nomeia o SHA                             |
| 2   | TLS         | apex e `www`: certificado da Amazon com SAN dos dois nomes, válido por ≥ 30 dias, TLS ≥ 1.2                          |
| 3   | Redirects   | `http://` → 301 `https://`; `www` → 301 apex com caminho e query; cadeia registrada                                  |
| 4   | Home        | 200, H1, âncoras do menu, console sem erro fora do frame do Turnstile (exceção de `B3`), zero resposta ≥ 400         |
| 5   | Assets      | todo asset referenciado 200 e `immutable`; `index.html`, `robots.txt`, `sitemap.xml` com `no-cache`; fontes carregam |
| 6   | Formulário  | iframe do Turnstile carrega; `GET /api/contacto` 405; `POST` sem token 400 (schema); `POST` com token falso 403      |
| 7   | SEO técnico | title, description, canonical, `og:*`, JSON-LD, `robots.txt`, `sitemap.xml`; `X-Robots-Tag: noindex` **presente**    |
| 8   | Cabeçalhos  | política de `B3`, conferida contra `CABECALHOS` de `scripts/infra/lib/cabecalhos.mjs`                                |
| 9   | 404         | caminho inexistente devolve 404                                                                                      |

O item 7 inverte em `B5`: depois do corte, `X-Robots-Tag` **ausente**. A spec de `B5` troca a
expectativa; este bloco deixa a expectativa num lugar só.

## 5. Sequência de execução e deploy

1. **Backup.** João baixa do StackCP e guarda as cópias (D3). Claude registra hashes.
2. **Ensaio de restauração** (§4.3).
3. **Ensaio DNS** (§4.4), estágios 1 a 5, e o procedimento de rollback escrito a partir dele.
4. **Domínio na distribuição.** `aws cloudformation validate-template`; change set sobre
   `lotus-site` com os parâmetros atuais e `ArnDoCertificadoDoDominio`. Esperado:
   `RedirecionarWww` em `Add` e `Distribuicao` em `Modify` sem `Replacement`. Qualquer outro recurso
   no change set para o fluxo.
5. **Smoke** contra `SMOKE_URL=https://lotusotec.cl` com `SMOKE_VIA`, e contra o domínio da
   distribuição sem `SMOKE_VIA`.
6. **Envio real** do formulário por João (D11).

Todo change set é executado por **João, ou por Claude com autorização explícita dada naquele
passo** — mesma fronteira do runbook, de `B2` e de `B3`.

**`7.2.4`** — `docs/infra/evidencia-smoke-<data>.md`:

- relatório do smoke com os nove itens verdes contra `lotusotec.cl` forçado para a distribuição e
  contra o domínio da distribuição, nomeando o SHA;

**Local, em todo `pnpm check`:** catraca de §4.2 verde, e reprovando com o nome do campo em fixtures

não roda `e2e/smoke/`.

**Limites declarados:**

- A restauração no host de produção não é exercitada (D4).
- O ensaio DNS prova o mecanismo num nome descartável; o corte de apex e `www` só acontece em `B5`.
- O smoke roda em Chromium.

## 8. Rollback do próprio bloco

- **Domínio na distribuição:** reverter o commit e reaplicar o stack. Antes de `B5`, nenhum visitante
  chega pela distribuição com o domínio próprio, então o raio é o próprio smoke. Falha no update faz
  o CloudFormation voltar sozinho.
- **Ensaio DNS:** o estágio 5 remove o nome. Se o bloco parar no meio, o registro sobra num nome que
  ninguém usa; o próximo passo é removê-lo, não reverter o apex, que o ensaio nunca toca.
- **Backup:** nada no ar muda.

## 11. Riscos

- **Route 53 recusar alias para nome fora dos `Aliases`.** Para o ensaio (D7).
- **O backup do StackCP não trazer o que o ensaio precisa** — dump parcial, arquivos sem
  `wp-config.php`. O ensaio falha alto no passo 2 e o pedido volta ao João com o que faltou.
- **PHP 7.4 é imagem sem suporte.** Serve para o ensaio porque é a versão do host; se a imagem sumir
  do registro, o ensaio para e isso vira decisão.
- **Plugin de segurança do WordPress bloquear acesso local.** Aparece no passo 4 de §4.3; a saída é
  desativar o plugin **na cópia**, registrado na evidência, nunca no host.
- **Certificado do ACM ainda não associado a nada.** O change set de §5 passo 4 é o primeiro uso; se
  o CloudFront recusar, nada no ar muda e o motivo vai para a evidência.
- **HSTS no navegador do João** depois do envio real por domínio forçado. Inofensivo: o WordPress
  também serve HTTPS até D8.
