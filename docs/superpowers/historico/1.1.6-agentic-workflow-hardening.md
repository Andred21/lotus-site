# EAP 1.1.6 — Endurecer workflow agentic e criar backlog operacional

## Objetivo

Executar dentro do próprio `lotus-site` o hardening do workflow agentic antes de avançar com a fundação funcional.

O objetivo é reduzir ao mínimo a dependência de prompts externos. O próprio repositório deve informar aos agentes:

- qual trabalho existe;
- qual trabalho está ativo;
- quais fontes consultar;
- como reconstruir contexto;
- como planejar;
- como executar;
- quais padrões arquiteturais/frontend respeitar;
- quando delegar ao Codex;
- como revisar;
- quais gates executar;
- quando bloquear;
- como fechar e registrar uma entrega.

Este work item deve ser tratado como **architectural**.

# Problema 1 — ausência de `backlog.md`

Criar:

```text
docs/superpowers/backlog.md
```

Ele será a fila operacional local do repositório.

Não substitui:

- Notion como roadmap externo;
- `state.md` como fonte única da fase;
- specs/plans como definição de execução;
- `progress.md` como histórico.

Modelo:

```text
Notion
  ↓
backlog.md
  ↓
state.md
  ↓
context packet
  ↓
brainstorm/spec/plan
  ↓
execução
  ↓
review
  ↓
closure
  ↓
progress.md
```

## Regras obrigatórias do backlog

- nunca promove automaticamente um item;
- nunca define `workflow_state`;
- contém somente trabalho ainda relevante;
- trabalho fechado sai da fila e permanece no histórico;
- registra origem: Notion, Git/review, débito técnico, harness, CI, segurança ou QA;
- registra dependências;
- registra escopo curto;
- registra DoD resumido;
- permanece pequeno;
- não replica todas as tasks do Notion.

# Problema 2 — arquitetura pouco objetiva

Endurecer `.claude/rules/architecture.md`.

Avaliar no brainstorming a seguinte estrutura:

```text
src/
├── app/
├── components/
│   ├── layout/
│   ├── sections/
│   └── ui/
├── content/
├── integrations/
├── lib/
└── assets/
```

Não criar diretórios vazios. Eles nascem apenas com consumidor real.

## Responsabilidades

```text
App
= composição

components/layout
= shell, Header, Footer e containers estruturais

components/sections
= seções completas da landing page

components/ui
= primitivas realmente reutilizadas

content
= conteúdo institucional/dados estáticos

integrations
= APIs, formulário, analytics e serviços externos

lib
= helpers puros sem React

assets
= assets gerenciados pelo Vite
```

## Direção de dependências a avaliar

```text
content -> não importa React
lib -> não importa React
ui -> não importa sections
sections -> não conhece provider externo diretamente
componente visual -> não executa integração diretamente
```

Não criar abstrações prematuras.

# Problema 4 — enforcement insuficiente

Avaliar `eslint.config.js` e adicionar somente catracas proporcionais.

Possíveis regras a avaliar:

- direção de imports;
- proibir `sections` importado por `ui`;
- impedir integração/fetch direto em componentes;
- impedir `content` importando React;
- limites proporcionais de complexidade/tamanho;
- manter `react-refresh/only-export-components`;
- imports proibidos entre camadas.

Toda nova dependência de lint deve justificar:

1. problema concreto;
2. por que ESLint/TypeScript atual não resolve;
3. custo de manutenção;
4. ganho esperado.

# Problema 7 — `site-review-task` insuficiente

A revisão deve verificar explicitamente:

## Acceptance
O critério de aceite foi realmente atendido?

## Scope
Há mudança fora do work item?

## Architecture
As fronteiras foram respeitadas?

## Componentization
- responsabilidade excessiva;
- extração prematura;
- duplicação;
- abstração sem valor.

## Dependency direction
Imports respeitam camadas?

## TypeScript
- `any`;
- casts sem justificativa;
- tipos duplicados;
- imports type;
- estados inválidos;
- props desnecessárias.

## React
- efeito desnecessário;
- estado derivável armazenado;
- dependências de efeito;
- composição inadequada;
- lógica excessiva no JSX.

## A11y / Responsive
Quando houver UI.

## Visual evidence
Quando Playwright existir.

## Testing
Cobertura proporcional ao comportamento.

## Overengineering
Detectar abstrações, wrappers e bibliotecas sem consumidor/necessidade.

## Severity

```text
blocking
important
suggestion
```

Reviewer deve citar evidência concreta, não preferência pessoal.

# Workflow obrigatório

Este documento não substitui o harness.

## 1. Planejamento

Na IDE, dentro do Claude Code:

```text
/planejar-site 1.1.6
```

Classificação esperada:

```text
architectural
```

Use:

```text
using-superpowers
→ brainstorming
→ aprovação do design
→ spec
→ writing-plans
```

Não implemente durante `/planejar-site`.

## 2. Aprovação

Apresente design e spec dentro da própria sessão Claude e aguarde aprovação humana.

## 3. Execução

Depois:

```text
/executar-site 1.1.6
```

Handoff esperado:

```text
executor: claude
reviewer: codex
```

O work item altera o próprio harness, portanto Claude deve ser o executor.

## 4. Revisão

Depois:

```text
/revisar-site 1.1.6
```

Codex revisa de forma independente. Claude verifica achados no diff real.

## 5. Fechamento

Com review limpo:

```text
/fechar-site 1.1.6
```
